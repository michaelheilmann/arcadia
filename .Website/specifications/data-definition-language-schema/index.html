Data Definition Language Schema (draft, v0.2)

1 Introduction

This specification defines the Data Definition Language Schema (DDLS), a declarative way to describe constraints on values written in the Data Definition Language (DDL). It is intended for readers of DDL who need to describe or validate structured data.

A DDLS schema is itself written as a DDL value. A DDLS reader interprets that value as a schema; a validator then checks a separate DDL value against a named schema. Read the DDL semantical translation first for the DDL value model. This page describes DDLS values and validation, not a replacement for the DDL lexical or syntactical rules.

For orientation, the reader accepts a top-level DDL map with kind: "Schema", a schema name, and a definition map. The schema translation and the other type descriptions explain how DDLS values are read; the validation section describes acceptance.

2 Notation

This specification describes DDL values as defined by the DDL semantical translation. Names such as kind and name denote entries in a DDL map; quoted words such as "Map" denote DDL string values. A DDLS value is the interpretation of a DDL schema description, not the DDL value being validated.

DDLS definitions have these kinds: Any, Boolean, Choice, List, Map, Number, SchemaReference, String, and Void. The scalar kinds are Boolean, Number, String, and Void; List and Map are aggregate kinds. A Schema names a definition; a MapEntry describes one entry within a map definition. Neither is itself a definition kind.

3 Semantics

The following sections describe how a DDL map is interpreted as a DDLS schema or definition. If a required field is missing, has the wrong kind, or a nested definition cannot be read, translation fails. The following error categories describe language outcomes.

ErrorMeaning
InvalidDefinitionErrorA schema description cannot be interpreted as a valid definition.
SchemaNotFoundErrorA referenced or starting schema is unavailable.
SchemaAlreadySpecifiedErrorA schema name is specified more than once.

ValidationErrorA DDL value fails to satisfy a usable schema.

3.1 Any type

A DDL map with the single entry kind: "Any" describes the DDLS Any definition. It accepts any DDL value during validation.

3.2 Boolean type

A DDL map with the single entry kind: "Boolean" describes the DDLS Boolean definition. It accepts DDL boolean values.

3.3 Choice type

A DDL map with kind: "Choice" and a choices entry describes a DDLS choice definition. The choices value must be a non-empty DDL list. Read each list element, in order, as a DDLS definition; the resulting list is the choice's alternatives.

If the list is empty, or if an element cannot be read as a DDLS definition, report InvalidDefinitionError during schema translation.

3.4 List type

A DDL map with kind: "List" and an elements entry describes a DDLS list definition. The elements value must be a DDL map describing a DDLS definition; it specifies the type of every element in the DDL list being validated. If that nested description cannot be read as a DDLS definition, report InvalidDefinitionError.

3.5 Map type

A DDL map with kind: "Map" and an entries entry describes a DDLS map definition. The entries value must be a DDL list of map-entry descriptions. Read each list element as a MapEntry, retaining its order. If an element is not a valid MapEntry, report InvalidDefinitionError. Two entries with the same name do not form a valid map definition.

3.5.1 Map entry

Each map-entry description is a DDL map containing kind: "MapEntry", a string name, and a type map that describes a DDLS definition. The entry may also contain optional. If present, optional must be a DDL Boolean value, expressed by the unquoted keyword true or false, as defined by the DDL Boolean semantical translation. It must not be a DDL String, Number, Void, List or Map value. If absent, optional defaults to false. Entry fields are matched by name, regardless of their order in the DDL map.

Map entry translationScroll horizontally if needed.
Optional fieldResult
Absent or falseA required entry with the given name and type.
trueAn optional entry with the given name and type.
Any non-Boolean valueThe entry description is invalid; report InvalidDefinitionError during schema translation.

The type map must itself be a valid DDLS definition. An invalid nested definition makes the map-entry description invalid.

For a valid MapEntry, the flag controls only whether the named entry may be absent from a DDL map being validated. It does not change the entry's type or supply a default value. Every present entry must satisfy its declared type, whether optional or required. In particular, a present DDL void value satisfies an entry of type Void but not an entry of type String. The DDL map value validation rules continue to reject unknown entries and missing required entries.

Examples (schema translation): The following MapEntry descriptions are valid:

{ kind: "MapEntry", name: "label", type: { kind: "String" }, optional: true }
{ kind: "MapEntry", name: "label", type: { kind: "String" }, optional: false }
{ kind: "MapEntry", name: "label", type: { kind: "String" } }

Examples (validation): Consider the following Map definition:

{
  kind: "Map",
  entries: [
    { kind: "MapEntry", name: "label", type: { kind: "String" }, optional: true },
    { kind: "MapEntry", name: "present", type: { kind: "Void" } }
  ]
}

The DDL value { present: void } is accepted because label may be absent and present matches Void. The value { label: "x", present: void } is also accepted. The value {} is rejected because the required entry present is absent. The values { label: void, present: void } and { present: "x" } are rejected because present entries must match their declared types. The value { present: void, extra: 1 } is rejected because unknown map entries are not permitted.

3.6 Number type

A DDL map with the required entry kind: "Number" describes the DDLS Number definition. It accepts DDL number values that satisfy every specified numeric bound.

3.6.1 Numeric bounds

A Number definition is a DDL map with required kind: "Number" and at most one entry of each of these optional fields: minimum, exclusiveMinimum, maximum and exclusiveMaximum. Every present bound must be a DDL Number value. DDL's existing duplicate-map-name restriction applies. The handling of unrelated definition fields is unchanged.

{ kind: "Number", minimum: 0, exclusiveMinimum: 5, maximum: 10, exclusiveMaximum: 10 }

For numeric comparison, let N(x) be the exact mathematical finite decimal denoted by the DDL Number spelling x, equivalently its signed integral significand multiplied by a power of ten. DDL Number values retain their original text, according to DDL Number semantical translation. Numeric order must be exact, with no lexical string ordering or loss of digits through conversion to machine floating point. Consequently N(+01) = N(1.0) = N(1e0) and N(-0) = N(0). Values of other DDL kinds are never coerced to Number.

A DDL value satisfies a bounded Number definition exactly when it is of DDL Number kind and all present bound conditions hold:

  • minimum: a: N(value) >= N(a).
  • exclusiveMinimum: a: N(value) > N(a).
  • maximum: b: N(value) <= N(b).
  • exclusiveMaximum: b: N(value) < N(b).

Inclusive and exclusive bounds may coexist on the same side and remain conjunctive. An absent bound imposes no condition. The { kind: "Number" } form accepts every DDL Number value. A DDL value outside a valid bound intersection fails with ValidationError.

During schema translation, report InvalidDefinitionError if any bound is not a DDL Number or if the conjunction of bounds defines an empty interval. For example, minimum: 2, maximum: 1 and minimum: 1, exclusiveMaximum: 1 are invalid; the single-point inclusive interval minimum: 1, maximum: 1 is valid. All supplied bounds must participate in the emptiness check.

The same rule applies to bounded Number definitions nested in Schema.definition, List.elements, MapEntry.type, or Choice.choices, and through SchemaReference. It does not otherwise alter containing-construct, choice or reference-resolution semantics.

A Number definition imposes no integer-only rule, multipleOf condition, or other numerical restriction unless specified by its four numeric bounds. The DDL Number grammar does not admit NaN or Infinity as numeric literals. Numeric magnitude and exponent have no fixed machine-width limits. Resource exhaustion produces an implementation resource error rather than an approximate or incorrect comparison.

3.7 Schema type

A DDL map with kind: "Schema", a string name, and a definition map describes a named DDLS schema. The definition map must describe one of the DDLS definition kinds in this section. If the name or definition cannot be read, or the definition does not describe a DDLS value, report InvalidDefinitionError during schema translation. A malformed schema description is not a validation failure of a DDL value.

3.8 Schema reference type

A DDL map with kind: "SchemaReference" and a string name describes a DDLS schema reference. The name identifies the schema to use when this definition is validated; the reference is not itself the referenced schema's definition.

3.9 String type

A DDL map with kind: "String" describes the DDLS String definition. Without an enum entry, it accepts every DDL string value. The optional enum entry restricts acceptance to an explicitly enumerated set of DDL strings.

3.9.1 String enumeration

If present, enum must be a non-empty DDL list whose every element is a DDL string. A malformed enum entry makes the String definition invalid at schema translation time and must report InvalidDefinitionError, not ValidationError. A missing enum does not restrict the String definition. No non-string value may be converted into a string to satisfy this rule.

All members of enum must be pairwise distinct. Equality compares decoded DDL String values as exact sequences of Unicode scalar values, case-sensitively. It does not compare source spellings or UTF-8 byte representations, and it performs no Unicode normalization, case folding, locale-specific comparison or trimming. Consequently, "A" and "\u{41}" denote the same member and must be rejected as duplicates. The precomposed string "\u{E9}" and the string "e\u{301}" remain different members. Two copies of the same text, including the empty string "", are duplicates regardless of their positions in the list.

A valid enumerated String definition accepts a DDL value if and only if that value has DDL kind String and its decoded value equals at least one enum member under the preceding equality rule. Otherwise validation must report ValidationError. Enumeration members are not schema references or alternatives: they are literal String values. Their order does not change acceptance or rejection.

Schema translation must reject an invalid enumeration even if the definition occurs in a Choice alternative that would not be selected for a particular input. An enumerated String definition nested within a List, MapEntry type or named schema, including a target reached through SchemaReference, has the same rules. Schema reference resolution and cycle checks apply to those definitions.

A String definition without an enum entry accepts every DDL String value. When enum is present, it restricts the accepted values to its members. A String definition imposes no pattern, length, or other restriction.

3.9.2 Conformance cases

The following cases define acceptance and rejection.

// Valid schema definition: accept "Nearest", "Linear", "Cubic" only.
{ kind: "Schema", name: "Filter", definition: {
  kind: "String", enum: ["Nearest", "Linear", "Cubic"]
} }

// Valid schema definition: unrestricted String.
{ kind: "Schema", name: "AnyString", definition: { kind: "String" } }

// Valid schema definition: an empty string is a permitted member.
{ kind: "String", enum: ["", "Other"] }

// Valid schema definition: canonically equivalent text is not normalized.
{ kind: "String", enum: ["\u{E9}", "e\u{301}"] }

With Filter selected, the separate DDL values "Nearest" and "Linear" are accepted; "nearest", "Unknown", 1, and void fail validation. With AnyString selected, every DDL String value is accepted and a non-String value fails validation.

// Invalid definitions: InvalidDefinitionError at schema translation.
{ kind: "String", enum: [] }
{ kind: "String", enum: "Nearest" }
{ kind: "String", enum: ["Nearest", 1] }
{ kind: "String", enum: ["Nearest", "Nearest"] }
{ kind: "String", enum: ["A", "\u{41}"] }
{ kind: "String", enum: ["", ""] }
{ kind: "String", enum: void }

Invalid DDL lexical or syntactical input remains an error of the DDL reader before DDLS schema translation. The DDL String definition governs escape syntax. DDLS error categories do not prescribe exact diagnostic message text or C API representations.

3.10 Void type

A DDL map with the single entry kind: "Void" describes the DDLS Void definition. It accepts DDL void values.

4 Validation

A validation context contains named schemas. Each schema has a name and a definition. Validation begins with one schema name and a DDL value to check. The elements field in a List definition describes each DDL list element; a Map definition has an entries list of named MapEntry definitions. Each map entry has a type and an optional flag.

4.1 DDL value validation

Validation has one successful outcome or an error. A successful outcome means that the DDL value satisfies the starting schema. An error means either that the value does not satisfy the schema or that the schema cannot be used. The error categories distinguish these cases.

Find the starting schema by name in the validation context. If none exists, report SchemaNotFoundError. If the context contains two schemas with the same name, report SchemaAlreadySpecifiedError. Otherwise validate the DDL value against that schema's definition as described below.

Example (accepted): Read this DDL value as a DDLS schema and register it under the name MySchema:

{ kind: "Schema", name: "MySchema", definition: { kind: "Any" } }

With MySchema selected, each of the following separate DDL values is accepted by Any:

true
[1, true, "w"]

Example (invalid schema): Replacing the definition with { kind: "Choice", choices: [] } makes the schema description invalid during reading; it is not a rejected DDL value. This is an InvalidDefinitionError.

4.2 DDLS value validation

Check the DDLS definition against the DDL value as follows. When a check fails, report a ValidationError unless a more specific schema error applies.

Validation by definition kindScroll horizontally if needed.
DDLS definitionWhen the DDL value satisfies it
AnyAny DDL value satisfies it.
Boolean, VoidThe DDL value has the corresponding kind.
NumberThe DDL value is a Number and satisfies every present numeric bound.
StringThe DDL value is a String and, if an enum is present, its decoded text equals one of the enumerated members.
ListIt is a DDL list and its elements satisfy the list rule.
MapIt is a DDL map and its entries satisfy the map rule.
ChoiceAt least one alternative satisfies the DDL value.
SchemaReferenceThe referenced schema's definition satisfies the DDL value; see schema reference resolution.

For a Choice, alternatives are considered in their listed order. An ordinary mismatch allows the next alternative to be tried; the first matching alternative accepts the value. If none matches, report a ValidationError. A structural schema error is not an alternative mismatch and stops validation, even if the erroneous alternative would not be tried after an earlier match. An empty choices list is rejected during schema translation, before validation.

4.3 DDL list value validation

A List definition applies only to a DDL list. Each list element must satisfy the definition in elements. Check the elements in order and stop at the first failure; an empty DDL list satisfies this rule.

4.4 DDL map value validation

A Map definition applies only to a DDL map. Its entries list must not describe the same name twice; a duplicate name makes the schema definition invalid. The DDL map must not contain duplicate names either.

  • Every DDL map entry must have a matching name in the schema's entries list. Unknown entries fail validation.
  • Every schema entry whose optional flag is false must be present in the DDL map. An optional entry may be absent.
  • Every present entry, including an optional one, must satisfy its type definition. Stop at the first failure.

The optional flag defaults to false; see the MapEntry translation for its DDL representation.

4.5 Schema reference resolution

A SchemaReference names a schema in the validation context. Register the intended schemas before validating a value; this permits forward references between their definitions. Then check every definition reachable from the starting schema, including all choice alternatives, list element definitions, and both required and optional map entry types. Unrelated schemas that cannot be reached from the starting schema are not part of this check. If any referenced schema name is unavailable, report SchemaNotFoundError. If a schema-reference cycle is reachable, report CyclicDefinitionError. Shared references reached along different acyclic paths are not cycles. When these checks succeed, validate each reference against its named schema's definition.

4.6 Acceptance and rejection

A DDL value is accepted if validation succeeds. A ValidationError rejects the value. An unavailable, duplicate, invalid, or cyclic schema is an error in the validation context or schema description; it does not produce an acceptance verdict.

The error categories specify language-level outcomes without prescribing an implementation interface or diagnostic wording.

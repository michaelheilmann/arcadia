Arcadia Program Definition Language

The Arcadia Program Definition Language (Arcadia PDL) is the declaration and instruction language consumed by the current compiler implementation in PDLC. The command-line interface for that compiler lives in PDLC.CLI.

This specification records the language accepted by the current compiler implementation as far as it can be inferred from the scanner, parser, and checked-in .mil inputs. Changes to accepted Arcadia PDL source syntax, lexical words, instruction forms, or primitive semantics in PDLC should be reflected here. It intentionally does not include the older HLL package, expression, or symbolic-operator grammar because those productions are not accepted by the current parser.

Notation

Grammar productions use single quotes for literal words and symbols. The suffix * means zero or more occurrences, ? means an optional occurrence, and alternatives are separated by |.

Translation

A program of the Arcadia PDL language is translated into declarations. This translation happens in three phases: The lexical translation translates Unicode code points to words. The syntactical translation filters the resulting sequence of words and then translates these words into a sentence. The semantical translation translates sentences into typed declarations.

Module Directories

A compiler invocation supplies one or more module directories. A module directory is the root directory of one Arcadia PDL module. If a supplied module directory path is relative, it is interpreted relative to the compiler invocation's working directory.

Each module directory contains a required compilation unit named Module.mil. The compiler parses this file before the other compilation units of the module. If Module.mil is not a regular file, the compiler reports an error.

The compiler discovers the remaining compilation units of a module by recursively enumerating the Library/Sources directory below the module directory and selecting regular files with the .mil extension. These files are parsed as compilation units of the same module.

The current implementation therefore uses the following directory shape:

<module-directory>/
  Module.mil
  Library/
    Sources/
      ... *.mil

Module.mil must contain exactly one module definition. A missing module definition is an error. More than one module definition is an error. A module definition in any other compilation unit of the module is an error. The name of the module definition does not have to match the names of declarations in Library/Sources.

Lexical Translation

The input is read as Unicode code points from UTF-8 bytes. Arcadia PDL selects reusable productions and translation rules from Common Lexical Translations unless this section defines a more specific Arcadia PDL rule.

Arcadia PDL defines its own lexical word alternatives and start symbol using the selected common categories and the PDL-specific categories below. The common specification does not supply a universal word production. PDL's reserved-word and other disambiguation rules belong to this consuming language.

Arcadia PDL uses the common definitions for whitespace, line terminators, line continuations, single-line comments, multi-line comments, periods, parentheses, curly brackets, colons, commas, boolean literals, and the void literal. Whitespace and comments separate words and are otherwise ignored by the parser. Line terminators are significant as statement terminators unless a line continuation joins the statement with the following line.

whiteSpace : Lexical.Whitespace
lineTerminator : Lexical.LineTerminator
lineContinuation : Lexical.LineContinuation
singleLineComment : Lexical.SingleLineComment
multiLineComment : Lexical.MultiLineComment
period : Lexical.Period
leftParenthesis : Lexical.LeftParenthesis
rightParenthesis : Lexical.RightParenthesis
leftCurlyBracket : Lexical.LeftCurlyBracket
rightCurlyBracket : Lexical.RightCurlyBracket
colon : Lexical.Colon
comma : Lexical.Comma
booleanLiteral : Lexical.Boolean
voidLiteral : Lexical.Void

Line Continuations

A line continuation is a reverse solidus immediately followed by a line terminator. The scanner produces one line continuation word that spans the reverse solidus and the line terminator, and the parser ignores that word. A reverse solidus that is not followed by a line terminator is a lexical error.

Statements may therefore be written over several lines by ending every line but the last with a line continuation. Only the line terminator of the last line terminates the statement:

invoke $0 print \
   c \
   "done"

Names and Identifiers

Arcadia PDL names are similar to Lexical.Name, but the current scanner also accepts an underscore as the first character without requiring a following alphabetic character. A qualified identifier is one or more names separated by periods.

name : ('A'..'Z' | 'a'..'z' | '_') ('A'..'Z' | 'a'..'z' | '0'..'9' | '_')*
identifier : name (period name)*

Registers

A register starts with $ and is followed by either a decimal register number or a name.

register : '$' ('0' | ('1'..'9' '0'..'9'*) | name)

Literals

The current scanner recognizes the common boolean and void literals and Arcadia PDL-specific integer, real, and string literal forms. Arcadia PDL integer and real literals are narrower than Lexical.Number: they do not have signs, and a real literal must start with one or more decimal digits followed by a period. Arcadia PDL string literals are narrower than Lexical.String: they use double quotes only and currently recognize only the escapes listed below.

integerLiteral : digit+
realLiteral : digit+ '.' digit* exponent?
exponent : ('e' | 'E') ('+' | '-')? digit+
stringLiteral : '"' stringCharacter* '"'
stringCharacter : anyCodePointExceptBackslashQuoteOrEndOfInput | '\\"' | '\\\\' | '\\n' | '\\r'

Reserved Words

The following words are reserved and cannot be used as names unless the scanner is changed:

add and class concatenate construct constructor divide entry enumeration extends false implements interface invoke isEqualTo isGreaterThan isGreaterThanOrEqualTo isLowerThan isLowerThanOrEqualTo isNotEqualTo jump jumpIfFalse jumpIfTrue loadArgument loadField method module multiply native negate not or procedure raise return set storeArgument storeField subtract true variable void

Syntactical Translation

Compilation Units

A compilation unit contains zero or more top-level definitions.

compilationUnit : definition* endOfInput
definition : moduleDefinition | classDefinition | enumerationDefinition | interfaceDefinition | procedureDefinition

Modules

A module definition names a module. The current parser accepts an optional empty body.

moduleDefinition : 'module' identifier moduleBody?
moduleBody : '{' '}'

Classes

A class definition names a class, may name an extended class, and may contain fields, constructors, and methods.

classDefinition : 'class' identifier ('extends' identifier)? ('implements' interfaceNames)? classBody?
classBody : '{' classMemberDefinition* '}'
classMemberDefinition : fieldDefinition | constructorDefinition | methodDefinition
fieldDefinition : 'variable' name ':' identifier

A class may implement one or more interface types. Every implemented interface type must be an interface type; the semantic analysis rejects any other symbol.

Not yet reflected by the C backend: the implements clause is parsed and semantically checked, but the current backend writer does not yet emit an implemented interface type set or the corresponding interface dispatch initializers. Classes are still written with Arcadia_defineObjectType.

Interfaces

An interface definition names an interface, may name the interface types it extends, and must contain operation definitions. The body of an interface definition is mandatory.

interfaceDefinition : 'interface' identifier ('extends' interfaceNames)? interfaceBody
interfaceBody : '{' interfaceMemberDefinition* '}'
interfaceMemberDefinition : operationDefinition
operationDefinition : 'method' nativeClause? name parameters? ':' identifier methodBody?
interfaceNames : identifier (',' identifier)*

An interface type may extend one or more interface types. Every extended interface type must be an interface type; the semantic analysis rejects any other symbol. The inheritance graph of interface types is acyclic, and an interface type may extend the same interface type at most once, transitively. The semantic analysis rejects a cyclic interface inheritance graph.

Each interface type has its own operation table. An interface type does not inherit the operations of the interface types it extends.

Enumerations

An enumeration definition names an enumeration and may contain named constants. A constant may have an integer initializer.

enumerationDefinition : 'enumeration' identifier enumerationBody?
enumerationBody : '{' enumerationConstantDefinition* '}'
enumerationConstantDefinition : name ('=' integerLiteral)?

Procedures, Constructors, and Methods

Procedures and methods declare a return type. Constructors do not. The declaration forms are:

procedureDefinition : 'procedure' 'entry'? nativeClause? identifier parameters? ':' identifier procedureBody?
constructorDefinition : 'constructor' nativeClause? parameters? constructorBody?
methodDefinition : 'method' nativeClause? name parameters? ':' identifier methodBody?
nativeClause : 'native' stringLiteral
parameters : '(' (parameter (',' parameter)*)? ')'
parameter : 'variable' name ':' identifier
procedureBody : block
constructorBody : block
methodBody : block
block : '{' statement* '}'

Statements

A statement is terminated by a line terminator, a closing curly bracket, or the end of input. Empty lines are ignored.

statement : variableDefinitionStatement | labelDefinitionStatement | instructionStatement
variableDefinitionStatement : 'variable' name
labelDefinitionStatement : name ':'
instructionStatement : instruction

Operands

Arcadia PDL instruction operands are not general expressions. They are literals, variables, or registers.

operand : booleanLiteral | integerLiteral | realLiteral | stringLiteral | voidLiteral | name | register

Instructions

The parser recognizes the following instruction forms. Conditional jumps preserve their condition operand in the AST; unconditional jumps have no condition operand.

instruction : (binaryInstruction
| unaryInstruction
| invokeInstruction
| constructInstruction
| jumpInstruction
| argumentInstruction
| fieldInstruction
| 'raise'
| returnInstruction) instructionTerminator
instructionTerminator : (Lexical.EndOfInput|Lexical.EndOfLine)
binaryInstruction : binaryOperator operand operand operand
binaryOperator : 'add' | 'subtract' | 'multiply' | 'divide' | 'and' | 'or' | 'concatenate' | 'isEqualTo' | 'isNotEqualTo' | 'isLowerThan' | 'isLowerThanOrEqualTo' | 'isGreaterThan' | 'isGreaterThanOrEqualTo'
unaryInstruction : unaryOperator operand operand
unaryOperator : 'negate' | 'not' | 'set'
invokeInstruction : 'invoke' operand name operand operand*
constructInstruction : 'construct' operand name operand operand*
jumpInstruction : 'jump' name
| 'jumpIfTrue' operand name
| 'jumpIfFalse' operand name
argumentInstruction : 'loadArgument' operand operand
| 'storeArgument' operand operand operand
fieldInstruction : 'loadField' operand operand operand
| 'storeField' operand operand operand
returnInstruction : 'return' operand?

An instruction is terminated by a line terminator of the line of its opcode. The line continuation symbol may be used to continue an instruction in the next line.

Semantical Translation

The semantical translation resolves the names of a sentence provided by the syntactical translation and binds every declaration to a type.

Type Names

Type names are fully qualified, and there is no relative resolution of type names. A type name is matched against the fully qualified names of the compilation as it is written, so Arcadia.Natural32 denotes a primitive type and MyModule.Greeter denotes the type declared with the qualified name MyModule.Greeter. A type name that does not spell out the fully qualified name of a type is not defined; for example, Greeter does not denote the type MyModule.Greeter. The same rule applies wherever the grammar expects a type name: a class extends or implements clause, an interface extends clause, a variable or parameter type, and the return type of a procedure, constructor, or method.

Member Names

A member of a class type is looked up by its declared name, unqualified, in the scope of the class type that declares it. A member name, unlike a type name, is never fully qualified.

Built-in Types

The following types are built in to every compilation. They are always spelled with the fully qualified Arcadia. prefix:

  • Arcadia.Boolean
  • Arcadia.Integer8, Arcadia.Integer16, Arcadia.Integer32, Arcadia.Integer64
  • Arcadia.Natural8, Arcadia.Natural16, Arcadia.Natural32, Arcadia.Natural64
  • Arcadia.Object
  • Arcadia.Real32, Arcadia.Real64
  • Arcadia.Void

Arcadia.Object is a class type; the other built-in types are primitive types.

A built-in type is provided by the runtime rather than by a module, so it is not generated: the compiler emits no source or header file for a built-in type, and instead binds a reference to it to the corresponding runtime type.

Native Definitions

A procedure, constructor, or method definition may carry an optional native clause. The clause takes a string literal naming the native target. A definition that carries the clause is a native definition; a definition that omits the clause is not native, even though it declares the same kind of member.

The string literal names the native target verbatim. It is an ordinary C identifier and is not subject to the qualified-name rules that apply to type names and to defined procedure, constructor, and method names. In particular, the rewriting that derives an implementation name from a fully qualified name by replacing the . separator does not apply to a native target name.

A native definition has no body to compile, because its body is provided by the named target. A definition without a native clause is provided with a compiler-generated body, which the current implementation leaves unimplemented.

A built-in type may declare members, and such a member is native without a native clause appearing in any compilation unit: a member supplied by a built-in type is native by being supplied, and not by carrying the optional clause.

Interface Operations

Interface operations are method declarations. The syntactical translation accepts the same surface method form as class methods, but semantical translation rejects an interface operation that has a method body.

Instruction Semantics

Arcadia PDL is currently dynamically typed. The semantical translation does not bind an instruction operand to a type, so the descriptions below state which operand forms an instruction accepts and which effect it has on the values of its operands at run time. An instruction raises an error when it cannot be applied to the values of its operands.

Arithmetic Instructions

add

The add instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation adds the value of the 3rd operand to the value of the 2nd operand and stores the result in the 1st operand. If the values cannot be added, then an error is raised.

subtract

The subtract instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation subtracts the value of the 3rd operand from the value of the 2nd operand and stores the result in the 1st operand. If the values cannot be subtracted, then an error is raised.

multiply

The multiply instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation multiplies the value of the 2nd operand with the value of the 3rd operand and stores the result in the 1st operand. If the values cannot be multiplied, then an error is raised.

divide

The divide instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation divides the value of the 2nd operand by the value of the 3rd operand and stores the result in the 1st operand. If the values cannot be divided, or if the value of the 3rd operand is zero, then an error is raised.

negate

The negate instruction expects two operands. The 1st operand must be a register, then 2nd operand must be a register or a literal. The operation negates the value of the 2nd operand and stores the result in the 1st operand. If the value cannot be negated, then an error is raised.

Concatenation Instructions

concatenate

The concatenate instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation concatenates the value of the 3rd operand to the value of the 2nd operand and stores the result in the 1st operand. If the values cannot be concatenated, then an error is raised.

Logic Instructions

and

The and instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores the logical conjunction of the values of the 2nd and the 3rd operand in the 1st operand. If the values cannot be combined by a logical conjunction, then an error is raised.

or

The or instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores the logical disjunction of the values of the 2nd and the 3rd operand in the 1st operand. If the values cannot be combined by a logical disjunction, then an error is raised.

not

The not instruction expects two operands. The 1st operand must be a register, then 2nd operand must be a register or a literal. The operation stores the logical negation of the value of the 2nd operand in the 1st operand. If the value cannot be logically negated, then an error is raised.

Relational Instructions

isEqualTo

The isEqualTo instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores true in the 1st operand if the values of the 2nd and the 3rd operand are equal, and false otherwise. If the values cannot be compared, then an error is raised.

isNotEqualTo

The isNotEqualTo instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores true in the 1st operand if the values of the 2nd and the 3rd operand are not equal, and false otherwise. If the values cannot be compared, then an error is raised.

isLowerThan

The isLowerThan instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores true in the 1st operand if the value of the 2nd operand is lower than the value of the 3rd operand, and false otherwise. If the values cannot be compared, then an error is raised.

isLowerThanOrEqualTo

The isLowerThanOrEqualTo instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores true in the 1st operand if the value of the 2nd operand is lower than or equal to the value of the 3rd operand, and false otherwise. If the values cannot be compared, then an error is raised.

isGreaterThan

The isGreaterThan instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores true in the 1st operand if the value of the 2nd operand is greater than the value of the 3rd operand, and false otherwise. If the values cannot be compared, then an error is raised.

isGreaterThanOrEqualTo

The isGreaterThanOrEqualTo instruction expects three operands. The 1st operand must be a register, then 2nd and 3rd operands must be registers or literals. The operation stores true in the 1st operand if the value of the 2nd operand is greater than or equal to the value of the 3rd operand, and false otherwise. If the values cannot be compared, then an error is raised.

Data Movement Instructions

Data movement instructions transfer a value into a target operand, which is always given as the first operand. The operand denoted by name is a declared name, not a register.

set

The set instruction expects two operands. The 1st operand must be a register or a variable declared in the enclosing procedure, constructor, or method, then 2nd operand must be a register, such a variable, or a literal. The operation stores the value of the 2nd operand in the 1st operand.

loadArgument

The loadArgument instruction expects two operands. The 1st operand must be a register, then 2nd operand must be a name denoting a parameter of the current procedure, constructor, or method. The operation loads the value bound to that parameter into the 1st operand. If the 2nd operand does not denote a parameter of the current procedure, constructor, or method, then an error is raised.

storeArgument

The storeArgument instruction expects three operands. The 1st operand must be a register, then 2nd operand must be a name denoting a parameter of the current procedure, constructor, or method, and the 3rd operand must be a register or a literal. The operation stores the value of the 3rd operand into the argument slot for that parameter of the entity identified by the 1st operand. If the 2nd operand does not denote a parameter of the current procedure, constructor, or method, then an error is raised.

loadField

The loadField instruction expects three operands. The 1st operand must be a register, then 2nd operand must be a register holding an object, and the 3rd operand must be a name denoting a field of the class type of that object. The operation reads that field into the 1st operand. If the 3rd operand does not denote a field of that class type, then an error is raised.

storeField

The storeField instruction expects three operands. The 1st operand must be a register holding an object, then 2nd operand must be a name denoting a field of the class type of that object, and the 3rd operand must be a register or a literal. The operation stores the value of the 3rd operand into that field. If the 2nd operand does not denote a field of that class type, then an error is raised.

Object Instructions

invoke

The invoke instruction invokes a method of an object. It expects the invoked object in its 1st operand in a register and the method to be invoked as its 2nd operand as name. The arguments, which may either be registers or literals, follow.

construct

The construct instruction invokes a constructor for the named class and stores the constructed object in the target operand. The 2nd argument is the name of the class of which the constructor shall be invoked. The third argument is a register containing the object upon which the constructor is invoked. The object is stored in the register specified by the first argument on success. The arguments, which may either be registers or literals, follow.

Control Flow Instructions

jump

The jump instruction expects one operand, which must be a name denoting a label declared in the body of the current procedure, constructor, or method. The operation transfers control to that label. If the operand does not denote a label declared in the current procedure, constructor, or method, then an error is raised.

jumpIfTrue

The jumpIfTrue instruction expects two operands. The 1st operand must be a register or a literal, then 2nd operand must be a name denoting a label declared in the body of the current procedure, constructor, or method. The operation transfers control to that label if the value of the 1st operand is true, and falls through otherwise. If the 2nd operand does not denote a label declared in the current procedure, constructor, or method, then an error is raised.

jumpIfFalse

The jumpIfFalse instruction expects two operands. The 1st operand must be a register or a literal, then 2nd operand must be a name denoting a label declared in the body of the current procedure, constructor, or method. The operation transfers control to that label if the value of the 1st operand is false, and falls through otherwise. If the 2nd operand does not denote a label declared in the current procedure, constructor, or method, then an error is raised.

raise

The raise instruction expects no operands. The operation raises the current exception.

return

The return instruction returns from the current method / procedure / constructor. It may have zero or one operand. It returns a void value with zero operands. If an operand is specified, that operand must be a register or a literal of which the value is returned.

The target of a jump must be a bare name; a string literal is not accepted. Labels are introduced by a label definition statement, that is by name ':', in the body of the enclosing procedure, constructor, or method.

Execution Model

This section captures the reusable interpreter model from the older material where it still matches Arcadia PDL instructions. It is descriptive until the compiler backend or runtime defines the behavior normatively.

The abstract machine supports string values, boolean values, signed integer values, unsigned natural values, real values, void, and procedure values. Integer and natural values may use 8, 16, 32, or 64 bit widths. Real values may use 32-bit or 64-bit IEEE 754 formats.

An interpreter may provide a stack. The stack is initially empty and supports querying its size, pushing a value onto the top of the stack, and popping the top value. Popping an empty stack is undefined.

An interpreter may provide a status variable with the states success and failure. The initial state is success.

Calling Convention

The old stack calling convention is retained as an abstract model for procedure invocation:

  1. The caller pushes arguments from left to right.
  2. The caller pushes the number of arguments.
  3. The caller pushes the procedure value.
  4. The invoke operation calls the procedure.
  5. The procedure pushes zero or more return values from left to right and returns with success or failure.
  6. The caller removes return values, the procedure, the number of arguments, and the arguments.

Arithmetic

For unsigned natural values of width n and m, add, subtract, and multiply compute the mathematical result modulo 2k, where k = max(n,m). The result is represented as an unsigned natural value of width k.

For signed integer values of width n and m, operands are sign-extended to width k = max(n,m). Addition, subtraction, and multiplication use two's-complement arithmetic and keep the low-order k bits of the mathematical result.

For division, division by zero raises an arithmetic error. Otherwise the operation computes the quotient according to the selected integer or natural arithmetic model and represents it at width k = max(n,m).

The unary negate operation computes zero minus its operand in the operand's arithmetic domain. The unary not operation is the logical negation operation.

Examples

module Arcadia.Engine {
}

class Arcadia.Engine.Event extends Arcadia.Object {
  variable timestamp : Arcadia.Natural64

  constructor(variable timestamp : Arcadia.Natural64)
}

enumeration Arcadia.Engine.Visuals.WindingMode {
  Clockwise = 0
  CounterClockwise = 1
}

procedure sum(variable x : Arcadia.Integer32, variable y : Arcadia.Integer32) : Arcadia.Integer32 {
  loadArgument $1 x
  loadArgument $2 y
  add $1 $1 $2
  return $1
}

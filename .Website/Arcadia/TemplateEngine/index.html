Arcadia Template Engine

The Arcadia Template Engine evaluates UTF-8 templates into text files. It is used to generate the Arcadia documentation website and other build-time artifacts. This reference describes the current implementation.

Introduction

Build the Arcadia Template Engine from the repository root using CMake. The command-line executable is the target Arcadia.TemplateEngine.CLI:

cmake -S . -B build
cmake --build build --target Arcadia.TemplateEngine.CLI

The executable's location depends on the generator and configuration. The examples below assume it is on PATH. For multi-configuration generators, pass --config Debug or the selected configuration.

First template

Create a UTF-8 file named hello.te containing:

<h1>Hello, @{project}!</h1>

Create an environment file named example.env, using the Arcadia Data Definition Language (DDL) map syntax:

{
  project : "Arcadia",
}

Invoke the CLI with source, target, dependency output, and environment paths. The following is a POSIX-shell example: enclosing each argument in single quotes passes its inner double quotes through to Arcadia's command-line parser. Adapt argument quoting for other shells.

Arcadia.TemplateEngine.CLI '--source="hello.te"' '--target="hello.html"' '--dependencies="hello.d"' '--environment="example.env"'

The file hello.html then contains:

<h1>Hello, Arcadia!</h1>

hello.d records the template inputs for incremental builds. The destination directory must exist; an existing regular target file is overwritten. All paths in this example are relative to the process's working directory. To render a template without user-defined variables, omit --environment.

Run the tests and build the documentation

ctest --test-dir build -R TemplateEngine --output-on-failure
cmake --build build --target Arcadia.TemplateEngine.BuildDocs

When building with a multi-configuration generator, use the matching CTest configuration (for example ctest -C Debug). Generated documentation is written to .Website/Arcadia/TemplateEngine/index.html. The page sources in Tools/TemplateEngine/Documentation are authoritative; do not edit generated HTML as the primary source.

Concepts and Terms

Template
A UTF-8 text file containing ordinary text and embedded directives. Ordinary text is copied to the output in order.
Directive
A construct beginning with @ in template source. In template source, @{name} loads a variable and @{procedure("argument")} invokes a procedure.
Environment
A collection of named values. An optional DDL map file supplies string-valued variables; built-in procedures come from the default environment. User-defined names can shadow built-in names.
Include
A directive that inserts the evaluated content of another template. Paths are interpreted relative to the Template Engine process working directory, not relative to the including template.
Target
The text file receiving the rendered output of an invocation.
Dependency file
The build dependency description identifying the target and all directly and transitively read template files. It enables incremental rebuilds and must not be confused with rendered output.

The CLI processes one top-level source template per invocation. Included templates share the invocation's environment and contribute to the same output file. See Template Language for the supported constructs and Module Interface for the command-line and build integration.

Specification

This section describes the behavior implemented by the current scanner, parser, evaluator, and CLI. Constructs identified as future work are not part of the current language.

Template Language

A template is a sequence of ordinary UTF-8 text and directives. Ordinary text passes to the output unchanged. The current directives are:

Source spellingEffect
@@Emit one literal @ character.
@{name}Load the named environment variable and emit its string value.
@{procedure()}Invoke a no-argument procedure and emit its result.
@{procedure("text")}Invoke a procedure with one string-literal argument and emit its result.

In the invocation form, the parser accepts zero or more string-literal arguments separated by commas. A name without parentheses denotes a variable load; a name followed by parentheses denotes an invocation. Numeric arguments and user-authored procedure definitions are not currently supported by the parser. Whitespace and quoting must follow the accepted scanner grammar.

An undefined variable, an attempt to invoke a non-procedure, a syntax error, or an invalid procedure argument causes evaluation to fail. Template content is evaluated from left to right; a failure prevents successful completion of the invocation.

Environment and name resolution

An optional environment file is parsed as an Arcadia DDL value of type Map. Every entry value must be a DDL string. An absent environment file yields no user variables; built-in procedures remain available. Names in the supplied environment shadow names in its enclosing default environment, including built-in procedures.

{
  title : "Arcadia",
  description : "Template example",
}

Use @{title} to insert the value of title. Invoking that string as @{title()} is an error.

Built-in procedures

All date/time procedures below take no arguments and use UTC. Values are evaluated when the procedure runs, not frozen when processing starts.

ProcedureResult
include("path")Evaluate and insert a file; one string argument, resolved relative to the process working directory.
dayOfWeek()Weekday number, Monday = 1 through Sunday = 7 (UTC).
dayOfWeekName()English weekday name (UTC).
dayOfMonth()Day number, 1 through 31 (UTC).
month()Month number, 1 through 12 (UTC).
monthName()English month name (UTC).
year()Four-digit year in the current Gregorian calendar (UTC).

include is handled by the evaluator rather than registered as an ordinary environment procedure. Recursive includes, including indirect cycles, fail rather than producing infinite output. Example:

<main>
  @{include("section.i")}
</main>

Output, dependencies, and failure behavior

The required dependency file describes the generated target as dependent on the source file and every transitively included file. It is designed for CMake dependency tracking (including Ninja depfiles); included templates are inputs, not additional generated targets. A change to a nested include therefore requires regeneration of the final output.

On a successful invocation the CLI writes the rendered target file and the dependency file. The target is overwritten if it already exists as a regular file. The CLI requires parent directories to exist and does not guarantee atomic replacement of the output. Read, parse, evaluate, and write failures cause an unsuccessful invocation; no rollback of output files is promised.

The CLI returns EXIT_SUCCESS on success and EXIT_FAILURE on failure. No stable numeric exit-code taxonomy or machine-readable diagnostics format is currently exposed. The present --help implementation prints usage but also returns failure. Do not interpret a nonzero status from --help as a render error.

Not currently supported

Loop directives, user-defined statements, general expressions, and user-defined procedures are possible future language extensions, not available features of this implementation.

Module Interface

Command-line interface

Arcadia.TemplateEngine.CLI [options]
OptionContract
--source="path"Required: UTF-8 input template.
--target="path"Required: rendered output file.
--dependencies="path"Required: output dependency file.
--environment="path"Optional: DDL map supplying string variables.
--helpPrint CLI usage; currently exits with failure.

The command-line parser expects double-quoted path values; ensure those quotes reach the application when invoking it from a shell. CMake's OnTemplateEngine integration handles argument construction. The CLI also recognizes --log, but its value is not currently used by the render path. It is not a supported logging interface.

Context stores source, target, and dependency paths and the evaluation environment. Context_onRun renders the configured source and writes the dependency description; the CLI writes the final target bytes. Environment_loadString parses a DDL map into variables. These are implementation-level C interfaces: callers must supply the normal Arcadia process/thread environment and error-handling discipline. This page does not promise a stable independent C ABI.

CMake integration

The preferred build-system interface is implemented by CMake/tools-template-engine.cmake:

BeginTemplateEngine(${MyProjectName}.Example.BuildDocs "Example")
  OnTemplateEngine("${CMAKE_CURRENT_SOURCE_DIR}/index.html.te"
                   "${REPOSITORY_SOURCE_DIR}/.Website/Example/index.html"
                   "${CMAKE_CURRENT_SOURCE_DIR}/website.env")
EndTemplateEngine()

OnTemplateEngine takes a source template, an output path, and an environment-file path. These arguments must be absolute in this CMake integration. Each generated page gets a dependency file containing its transitive template includes; the template and environment sources trigger rebuilds through the custom command.
